# Careers hiring cycle v2: runbook

This runbook covers how careers.isocodelabs.com's Round 1 pipeline is wired and how to run it day to day. Setup and going live are in [`deploy.md`](../deploy.md). Everything runs on GCP except Cloudflare (DNS, proxy, Turnstile) and Resend (email). Both of those stay on their free tiers.

## How it fits together

```
browser ──► careers.isocodelabs.com (Cloudflare) ──► Cloud Run (Next.js + Payload)
   │                                                     │
   │ 1. POST /api/careers/upload-url  (Turnstile, rate limit, role open?)
   │ ◄── signed POST policy + upload ticket ─────────────┤
   │                                                     │
   │ 2. POST CV straight to GCS (never through Cloud Run) ──► gs://<bucket>/pending/…
   │                                                     │
   │ 3. POST /api/careers/apply  (idempotent on submissionId)
   │      validate → HEAD + %PDF check → copy to applications/… → 1 insert
   │ ◄── { ok: true } ───────────────────────────────────┘
   │
founders ──► /admin/screening (Payload login) ──► signed GET URLs (10 min) for CVs
Cloud Scheduler ──► POST /api/careers/cron/digest (daily founders' email)
```

- **Pages.** `/careers` and `/careers/roles/<slug>` are statically generated with 60 s ISR. On the careers host, middleware maps `/`, `/roles/<slug>` and `/applicant-privacy` onto them. Changing a role in the admin revalidates its pages immediately on that instance; other instances catch up within 60 s.
- **Role status** (`open` / `paused` / `closed` / `archived`) is the only switch. The API reads it from the DB with a 10 s cache, so a paused role stops accepting applications within seconds. If a role has an `applicationCap`, it auto-pauses when the cap is reached.
- **Dedupe:** one application per `cycle:role:email` (unique index on `dedupeKey`). **Idempotency:** a unique `submissionId`, generated by the browser.
- **Rate limits** are per IP and kept in Postgres (`careers_ops.rate_limits`, an UNLOGGED table outside Payload's schema). They fail open; Turnstile is the main gate.
- **Logs** go to Cloud Logging as JSON with no PII. ERROR entries reach Error Reporting automatically.

## Setup, deploy and load test

All of it lives in [`deploy.md`](../deploy.md) as one ordered checklist. That covers Turnstile, the GCS buckets and IAM, secrets and build args, the staging clone, the migration rehearsal, the k6 load test, the production deploy, the smoke test, the daily digest and monitoring.

Two rules worth knowing even outside a deploy:

- **Connections:** Cloud Run max instances × `DB_POOL_MAX` must be at most Cloud SQL `max_connections` − 10.
- **Schema changes:** this repo has no Payload migrations folder. The schema is pushed whenever a script boots Payload outside production (e.g. `npm run careers:migrate`). Back up first, and read Drizzle's prompt before answering `y`.

## Day to day

- **Screening:** go to `/admin/screening`. Press `?` for the shortcuts: j/k to move, 1–5 to rate, s to shortlist, r to reject, p for in process, x to select, o to open the CV.
- **Pause or close a role:** use the status dropdown on the role card in the screening view, or open Careers → Job Openings. The change is live within 60 s, with no deploy needed.
- **Mail shortlisted candidates:** filter to Stage = Shortlisted, then click Export CSV.
- **Deletion request:** open the applicant, choose "Delete applicant data…" and type their email to confirm. This removes the record and every stored copy of the CV, and writes an audit entry with no PII (Careers → Careers Audit Log). It's the only hard delete in the system.
- **New hiring cycle:** set `CAREERS_CYCLE` (e.g. `2027-04`) and redeploy. The same people can then apply again, and earlier cycles stay filterable in the screening view.
- **Two-founder reviews:** every founder can review every applicant. Each review is separate: a decision (approve, maybe or reject), an optional rating and a note. The applicant's merged state follows from the reviews:
  - *Waiting for 2nd review*: one review so far.
  - *Agreed*: both reviews are approve, or both are reject. A "maybe" never overturns a firm decision.
  - *Discussion*: one approves and one rejects. Separate them with the Review filter and talk it through.
  - *Undecided*: both say maybe.
  The shared stage, tags and notes are unchanged. Saving your own review again updates it. The merge rules live in `src/lib/careers/review.ts`.
- **Retention:** keep rejected applicants' data for 12 months after the cycle closes. After that, founders review and bulk-delete. Nothing is deleted automatically.

## Deploying the review feature

It adds a table (`application-reviews`) and two columns on applications. Production doesn't push schema, so before the release goes live, dry-run and then apply `npm run careers:migrate` against production (see `deploy.md` step 7), the same as the careers v2 migration. Both changes are additive.

## Local development

`CAREERS_STORAGE=local` (the default outside production) stores CVs under `.local/storage`, using HMAC-signed URLs served by `/api/careers/dev-storage`, which returns 404 in production. Turnstile is skipped when no secret is set.

To test the screening desk at volume, run `npx tsx --env-file=.env scripts/careers-seed-fake.ts`. It seeds 10k fake applicants under cycle `qa-fake`, refuses to run against a non-local DB, and `--remove` deletes them again.
